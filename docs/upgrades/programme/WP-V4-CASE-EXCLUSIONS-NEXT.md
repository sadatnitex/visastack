## Must fix

1. Audit and stored rows must always agree (both reviews, Medium). `applyCaseSharingAnswers` (packages/services/src/sharing.ts ~819-900) decides "already recorded" from audit history keyed by `${kind}:${id}` without the event type, and inserts with onConflictDoNothing. Failures: yes-then-no writes the row with no GRANT_CASE_EXCLUDED; no, Allow, no leaves the last event as GRANT_CASE_EXCLUSION_REMOVED while the row exists; a repeat "yes" after "no" reports shared while the row stays. A restore replays the last event only, so the case reopens.
   Fix: make the answers ONE-SHOT per case: refuse (invalid, plain message) if any GRANT_CASE_EXCLUDED / GRANT_CASE_ALLOWED event already exists for that case; later changes go only through removeCaseException ("Allow This Case") and a new explicit "Stop Sharing This Case" path is NOT needed now. Audit exactly the rows actually inserted (`.returning()`). Tests for both scenarios plus the one-shot refusal; a restore test after the sequences.

2. Race between answering and invitation acceptance (security, Medium). Take `pg_advisory_xact_lock` on a key derived from the applicant id at the start of `applyCaseSharingAnswers` (before reading grants and invitations) and in `acceptSharingInvitation` (packages/services/src/sharing-invitations.ts, before reading the invitation), and in createGrant for all-cases grants and in creating an all-cases sharing invitation (see 4). Use one shared helper for the key. Document why. (PGlite cannot show the race; test that the lock call is made and ordering is correct via a db wrapper or by asserting the SQL.)

3. Revoked old grant keeps the excluded case's evidence requests visible (security, Medium). packages/services/src/agency.ts ~1614 `exists` ignores grant status. Fix: a request on a case is visible only if the organisation has a grant that can still give access (ACTIVE or PAUSED as the existing rules define; check how status is treated elsewhere) and covers the case under the one rule; keep the existing post-revoke behaviour (history visible after revoke) ONLY when the organisation has no live grant on the person at all. Test the security reviewer's scenario: request on C2 under G_old, revoke G_old, new all-cases G_new, exclude C2: the request must not be listed. Their proof test is in docs/upgrades/programme/WP-V4-CASE-EXCLUSIONS-POC/ (the security review proof tests, stored as .txt; port them into case-exclusion-enforcement.test.ts) (read it, port it into case-exclusion-enforcement.test.ts).

4. A new all-cases grant or invitation to the same recipient reopens the case (security, Medium). Rule: exceptions follow the RECIPIENT. When an all-cases grant or all-cases sharing invitation is created for a recipient (same organisation, or same person account / same invited email) who has exceptions on this applicant's cases under an earlier grant or invitation (live or revoked), copy those exceptions onto the new grant or invitation in the same transaction (audited as GRANT_CASE_EXCLUDED with a reason such as "carried forward"). A case-scoped grant for that exact case is an explicit share and is allowed to reach it. Display ("Not shared with ...") must be computed per recipient: a recipient appears as not sharing a case only when no live grant of that recipient reaches the case (Sharing page, Application Memory ~334-343, the case page note). Tests: re-share all cases after a "no" keeps the case hidden; a case-scoped grant for that case shows it and the "Not shared" label disappears.

5. Invitation-bound exceptions invisible to the owner (code review, Low). Show them read-only under each pending all-cases invitation on the Sharing page ("Not Shared: <case title>"), and include them in the account export next to the invitation if invitations are exported, otherwise as a separate list "case exceptions on pending invitations".

6. Restore fallback can be undone (code review, Low). When an exception cannot be rewritten during reconciliation, REVOKE the grant (not pause), as for invitations, write RECONCILIATION_CASE_EXCEPTION_FAIL_CLOSED, and document it in docs/operations/backup-resurrection-reconciliation.md (now on the allowlist) together with rows for GRANT_CASE_EXCLUDED, GRANT_CASE_ALLOWED and GRANT_CASE_EXCLUSION_REMOVED.
