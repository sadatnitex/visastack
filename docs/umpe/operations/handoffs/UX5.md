# UX5 hand-back: answers on the agency Document Requests list (no migration)

- Built on branch `ux5-answers`, from the head of main (UX3 merged). Local only, not pushed. Tables: none changed, no migration. One new read, one page change, one style block.
- What the agency sees (owners and admins only): a new Answers column on the Document Requests list. Each request shows its total ("3 Answers"), then one chip per state that has something: "2 Waiting for Review", "1 Needs Correction", "1 Accepted". A request with no answer shows a dash (spoken as "No Answers Yet"). When at least one request has answers waiting, a second filter group appears: All Answers and Waiting for Review with a count. It works with the existing status filter, each keeps the other in its links, and `?review=waiting` is ignored when it is not valid, when nothing is waiting, or for a member.
- What a member sees: nothing new. A member with May Request Documents gets no Answers column and no answers filter, and the page does not even make the read. Answers, files and decisions stay with owners and admins, as before.
- How an answer is counted (`packages/services/src/umpe-collection-answer-summary.ts`, `summariseCollectionAnswers`): a signed-in person's answer counts while it is not withdrawn or replaced and its request is not revoked (a closed request keeps its answers). A guest's submission counts while its request is not revoked. The latest decision on an answer (newest time, ties by id) is its state. No decision, or only Received, means Waiting for Review. Received is never shown as Reviewed or Accepted, and is not a state of its own on this list.
- Safety: the read takes the strict owner-or-admin scope check first (so a member, a copy of a scope, a stale scope and the switch turned off all get an empty result), needs an agency VisaStack has reviewed, only keeps valid ids (repeats removed, capped at the list limit), and checks every id against this agency's own requests. Every query is bound to the agency. It returns counts only: no names, ids, notes or file data. Before the answer or review tables exist, that source is skipped and nothing breaks. The signed-in answer count sits in `access/collection-response-access.ts` (`liveResponseDecisionCounts`, which checks the scope itself too), beside the other readers of the response table, because that table holds a person's id and the applicant access ratchet only allows such reads there. The access ratchet in `enforcement.test.ts` now lists the new function among the ones it must find and judge.
- Owner decisions defaulted (change on request):
  1. A guest who sends again is counted once: only the newest submission of each person counts, so an old unreviewed version never inflates Waiting. The older versions stay in the request's own answers panel as before.
  2. The list shows a total "N Answers" plus the three state chips, and "Received" is not a state on the list: an answer marked Received counts as Waiting for Review, because nobody has decided on it yet.
- Tests: 18 new service tests (both sources, withdrawn and replaced, every decision, later decision wins, guest resend, closed and revoked, member and other agency and unreviewed agency and switch off and copied scope, bad ids and the cap, missing tables) and 8 new page tests (column and counts, no word Reviewed or Accepted for waiting, member sees none and the read is never made, the filter alone and with status, a bad value). Proven red by breaking the real code, each then restored: removing the scope check from the service (the access ratchet and 3 service tests fail), changing the newest-guest-submission rule (the resend test fails), and loosening the member check on the page (the member test fails).
- Found while building: a column placed in a select list loses its table name in this query builder, so a correlated lookup that says `id` meant the other table's id and every decision read as none. The service names the table in full there, and the decision tests fail if that is undone.
- Not verified: a signed-in agency account in a browser, the phone card layout on a real screen (a rule makes the Answers cell a full-width row under 1180 px, built from the existing UX3 card), a screen reader, dark appearance, the e2e browser checks, query cost on a large production list.
