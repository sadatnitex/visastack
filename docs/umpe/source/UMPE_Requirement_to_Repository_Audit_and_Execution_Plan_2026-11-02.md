## A. Executive verdict and nomenclature

**UMPE** means *Unified Master Product & Experience*. It defines what must be delivered, not a parallel new database/product. The current code has a strong base in records, versions, case logic, agency invitations, branding and AI suggestions. The main missing end-to-end capabilities are: mixed-person 80+ file/folder ingestion with targeted exception review; fully verified route-specific requirement coverage and conditional mandatory/alternative rules; zero-friction individual and family packages; pre-client agency checklist issuance; truly account-free guest intake; Saturday official-source monitoring; and outcome evidence analytics. These are *not* achieved simply by changing the navigation or adding an AI model.

**Audit labels:** `BASE` = significant functionality implemented in source, runtime still to prove; `PARTIAL` = related code but incomplete UMPE journey; `GAP` = no direct implementation found in inspected source paths; `CONTENT-GAP` = official editorial data quality/coverage gap, cannot be solved by code; `POLICY` = directional lock; `VERIFY` = stronger cross-repository/runtime evidence needed before declaring missing; `UNVERIFIED` = requires real environment/browser/operational checks. **Not a quality score, deployment certification, or claim of exact global feature coverage.**

**Source truth warning:** Public `packages/core/src/destinations` catalog ≠ authoritative `packages/db/src/schema.ts` published pack requirements. The country intake README reports 156 countries, 61 routes, 85 lines, 16 routes with zero requirements and only four routes with at least five requirements; many are incomplete. This is good for discovery, *not submission-readiness authority*. The older 26-Oct handoff records one two-item non-authoritative published pack; **current live DB pack inventory remains unverified**. Never claim current route coverage from these figures.

## C. Critical architecture decisions (to prevent expensive rework)

1. **Maintain one canonical fact/document/mission/pack engine.** `applicants`, `facts`/`factVersions`, `documents`/`documentVersions`, `missions`/snapshots and `packs`/versions are preserved. Add orchestration, typed relations, source observations and request-scoped guest objects only where the existing schema cannot legitimately represent them. A guest must never be assigned a fake `applicantId` to satisfy a foreign key.
2. **Separate five kinds of truth.** (i) Uploaded source-observed text, (ii) user-approved facts, (iii) authoritative requirement version, (iv) selected/shareable exact document/fact version, (v) actual external submission/outcome evidence. A confident extraction is not a confirmed fact; a prepared package is not submitted; a recorded outcome need not be official proof.
3. **Avoid changing historical pack checksums.** `packs.ts` explicitly warns that adding keys to `buildManifest` changes prior published checksums. New necessity/group/rule representation needs a versioned serializer, sidecar schema, or compatible migration *designed and regression-tested before any write*. Existing published manifests continue verifying byte-for-byte.
4. **Keep categories separate from sharing scope.** Master Profile sharing `PROFILE_PACKS` are permission categories; new MECE taxonomic labels are content classification. They cannot be the same enum or automatically expand agency grants.
5. **Freeze evidence at decisions.** Existing secure blob-access tokens already pin `documentVersionId`; do not invent a vulnerability there. However agency `evidenceRequests.respondingDocumentId` and decision records lack a stable exact-version FK. Introduce version-pinned receipt references and distinguish link issuance from actual completed retrieval. Preserve legacy uncertainty, do not fabricate missing old IDs.
6. **Do not treat the static country data as a verified route pack.** User first-run/country browsing can present sourced preliminary facts with uncertainty. For actual submission-readiness, require an authoritative versioned pack with matching nationality, residence, application place, route, purpose and effective-date logic; otherwise offer honest manual/agency checklist mode.
7. **Check new rules safely.** `missions.ts` currently treats invalid condition AST as null and falls back to legacy behaviour. Continue supporting legacy data, but new authored/published UMPE rules must reject malformed conditions before they can be used for an affirmative readiness assessment.
8. **Guest intake is a bounded agency request, not an account.** New primitives proposed (naming subject to code audit): `collection_requests`, immutable `collection_request_versions`, `guest_access_challenges`, expiring `guest_sessions`, `collection_upload_items`, `collection_submissions` and `collection_review_events`. These are request-scoped, with bounded retention and explicit file grants, and can be linked to canonical cases *only after* verified traveller authorization and consent. Do not duplicate existing audit, storage, token/crypto, AI or organization policy implementations.
9. **Guest verification is separate from authentication registration.** A WhatsApp-shared link can safely show a neutral invitation and organization branding. Seeing private item details, returning to drafts and submitting sensitive documents require request-scoped recipient proof. Email OTP without an account is a candidate where email is available; phone proof requires an actual SMS/WhatsApp provider or separately accepted agency-verification mechanism. No claim that such a provider exists. Link possession alone is not proof of a named person's identity.
10. **Guest does leave bounded agency records.** No traveller-owned VisaStack timeline without registration; nevertheless authorized agency receipt, exact selected files, event log and regulated retention/deletion are mandatory. Consent cannot be inferred from uploaded folders, and guest records cannot be automatically adopted by an account based solely on email matching.
11. **Official source checks need a content programme.** `country-intake-pages.yml` is manually triggered and HTML fetcher skips PDFs. Make Saturday source monitoring a durable job with retries, snapshots and candidate diffs; keep material publication governed by existing author-reviewer rules. Editorial content and real qualified review capacity are prerequisites for claiming supported route coverage.
12. **UX must be a composition, not a rebuild.** Reuse `DepthScope`, agency brand helper, notifications, app nav, case forms, and existing profile/vault screens; change the primary entry point and connect actions. Keep existing menus, deep links and permissions reachable.

## D. End-to-end journeys and acceptance gates

**J1, individual traveller intake:** Drop 80 mixed files including a folder; statuses per item, safe format limitations, no 21st-file disappearance. Correctly associate 65+ real-classifiable test fixtures and leave deliberately ambiguous ones unresolved (numbers are *test fixture quantities*, not promised accuracy rates). Split duplicates, new-period statements, renewed passports and corrected scans correctly. Extract source-attributed profile proposals. Deny accidental cross-person updates and keep existing manual review.

**J2, trip and family:** State country, purpose, nationality/residence and dates; obtain the correct supported authoritative pack version. For three authorized people, derive separate requirement sets, necessary alternatives and individual exact-version evidence proposals. Shared booking linked only where explicitly authorized. Recommended evidence never blocks, conditional unknowns don't become green, and required missing items remain visible after user exclusions.

**J3, ongoing update:** A corrected scan, newer statement, expiring passport, resolved fact conflict or published rule revision recalculates only affected active packages. Send a single relevant explanation. Preserve every prior submitted/accepted snapshot and independent case handoff.

**J4, agency request for existing account:** Agency operator selects route/destination/purpose/tentative date, edits checklist and issues immutable request revision; recipient opens branded neutral preview, signs in with verified invited identity, selects own profile and explicitly shares only selected exact versions. Agency reviews, requests replacement and receives pinned audit history.

**J5, agency guest request:** Same issued request, but customer can use bounded guest verification without account; upload in multiple sessions from phone/desktop; classify automatically against the exact issued revision, correct mistaken mappings and explicitly submit. Agency sees receipt and review history. A forwarded URL alone cannot expose drafts, and guest data does not create a permanent account wallet.

**J6, source maintenance:** Saturday job checks registered official URLs (including changes, blocked HTML, PDFs and source disagreement), creates candidate diffs, records actual fetch time and reviewer action, publishes only approved version and flags affected live packages without altering issued documents.

**J7, field intelligence:** Two successive authority submissions with different evidence and outcomes remain two attempts, not one success. Guest and account-based data use accurate source/provenance denominators; missing outcomes remain unknown. Privacy-suppressed internal reporting distinguishes official requirements, agency additions and observed additional requests. No approval prediction.

**J8, role, safety, commercial acceptance:** Existing 2026-11-02 source HEAD passes current test/CI guard suite before change. Every PR runs unit/integration/access/a11y tests; final exact release has authenticated desktop/mobile E2E tests with real provider configuration appropriate to approved operations, agency and guest role separation, cross-tenant abuse tests, resilient upload recovery, retained deep links and existing billing/AI/profile/delete/restore operations. Deployment verification is independent of source inspection.
