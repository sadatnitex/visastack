# AI Gateway boundary map (PR 9)

Written for PR 9 (master directive: `commercial-recovery-completion-ux-directive.md`
§7 "PR 9 — OpenAI API quality and safety"). Documents what the AI Gateway
actually does today, what this PR closed, what it measured, and what
remains open — matching the honesty pattern of the other per-PR boundary-map
docs in this directory.

## 1. What is actually AI-driven today

The directive's "approved tasks" list names five capabilities: document
classification, filename component proposal, canonical field proposal,
conflict explanation, and grounded draft assistance for later mission
outputs. Of these, **only canonical field proposal is implemented through
the AI Gateway** (`AiExtractionPort` → `OpenAiExtractionAdapter` →
`runExtraction` in `packages/services/src/ai.ts`).

| Approved task | Status | Where |
|---|---|---|
| Canonical field proposal | **AI-driven** (OpenAI Responses API) | `AiExtractionPort.extract()` |
| Document classification | Deterministic, rules-based — **not** AI | `packages/services/src/classification.ts` (MRZ/pattern matching, `CONFIDENCE_THRESHOLD`; below threshold → `classifiedType: null`, never a guess) |
| Filename component proposal | Deterministic, template-based — **not** AI | `buildProposedName` (`packages/services/src/naming.ts`), called from `packages/services/src/intake.ts` only after classification clears review |
| Conflict explanation | Not implemented | Conflicts are recorded as structured data (`conflicts` table); no natural-language explanation is generated by anything yet |
| Grounded draft assistance for mission outputs | Not implemented | Mission outputs (letters, packs) are PR 10/11 scope |

This matters for reading the rest of this document correctly: the eval
harness below (§4) can only benchmark the one capability that is actually
AI-driven. Classification and filename proposal already have their own
deterministic test suites (`classification.test.ts`,
`document-naming.test.ts`) that assert correctness directly — they don't
need (and can't meaningfully receive) an AI benchmark, because no model call
is in their path.

## 2. Provider configuration

| Directive requirement | Status |
|---|---|
| Behind `AiExtractionPort` | ✓ — the only concrete implementation is `OpenAiExtractionAdapter` |
| Responses API | ✓ (`POST https://api.openai.com/v1/responses`) |
| `gpt-5.6-terra` | ✓ default (`DEFAULT_MODEL`), operator-overridable via `OPENAI_MODEL_PRIMARY` |
| Initial reasoning effort `low` | ✓ **fixed in this PR** — previously `reasoningEffort` had no default and was silently omitted from every request unless an operator remembered to set `OPENAI_REASONING_EFFORT`; now `OpenAiExtractionAdapter` defaults to `'low'` (`DEFAULT_REASONING_EFFORT`) the same way it already defaulted model and prompt version, still operator-overridable |
| Strict structured output | ✓ (`text.format.type: 'json_schema'`, `strict: true`, `additionalProperties: false` on every object in `PROPOSAL_SCHEMA`) |
| `store: false` | ✓ default, opt-in only via `OPENAI_STORE_RESPONSES=true` |
| Server-side key only | ✓ — adapter is `server-only`-guarded (`apps/web/src/lib/ai.ts`); no browser code path exists |
| Stable prompt versions | ✓ (`DEFAULT_PROMPT_VERSION`, a dated string bumped only on deliberate prompt changes) |
| Stable schema versions | ✓ **new in this PR** (`SCHEMA_VERSION = 'field_proposals_v1'`) — previously not tracked at all; now persisted per run (`ai_extraction_runs.schema_version`) and included in the cache key |
| Minimum necessary input | ✓ (unchanged) — only the deterministically-extracted, size-capped text and the field-key registry are sent, never raw file bytes |
| Deterministic processing first | ✓ (unchanged) — `runExtraction` requires prior successful deterministic extraction; there is no path that sends a document to the model without it |
| Manual fallback always | ✓ (unchanged) — every profile field remains directly editable regardless of AI availability (PR 7's workspace, PR 8's `editFact`) |

## 3. Cost controls

| Control | Status |
|---|---|
| Monthly hard limit | ✓ pre-existing (`AI_PILOT_MONTHLY_HARD_LIMIT_USD` → `aiBudgetLimitUnits()`); `runExtraction` refuses once the durable ledger total meets or exceeds it. **Fixed in PR-C2** (finding #20, post-programme defect register): the check is now also serialized platform-wide by a second, fixed-key `pg_advisory_xact_lock`, not only per-document — previously, concurrent requests for *different* documents could each read the same pre-commit total and all pass, overshooting the cap by more than the intended one-at-a-time margin |
| Per-document limit | ✓ pre-existing (`AI_PER_DOCUMENT_LIMIT_USD`) |
| Attempt limit | ✓ pre-existing (`AI_MAX_ATTEMPTS`). **Fixed in PR-C2** (finding #28): a cache hit's own free `aiExtractionRuns` row no longer counts against it — `countAiExtractionAttempts` excludes `servedFromCacheRunId`-set rows, and the gate itself now only runs on a genuine cache miss, so a cache-hit-eligible request can never be refused merely because the code hadn't yet discovered it would cost nothing |
| Page limit | ✓ pre-existing (`AI_MAX_PAGES_PER_DOCUMENT`) |
| Cache | ✓ **new in this PR** — see §5 |
| Duplicate prevention | ✓ — by design, the same mechanism as caching: re-running extraction on the same document version under the same model/prompt/schema/reasoning config produces the same cache key, so it's served from the existing run rather than re-invoking the model. This is distinct from (and in addition to) the pre-existing PR 6 advisory-lock guard against two *concurrent* requests double-spending before either has recorded its attempt |
| Usage ledger | ✓ pre-existing (`ai_extraction_runs`, summed by `totalAiCostUnits`) |
| Admin warning | ✓ **new in this PR** — `AI_PILOT_MONTHLY_WARNING_USD` / `aiWarningLimitUnits()`, defaulting to 80% of the hard limit (matching the platform storage quota's warn/hard-stop ratio); surfaced as a distinct meter on the admin page (`apps/web/src/app/app/admin/page.tsx`, "AI Gateway spend" card) alongside the hard cap |
| Capability shutoff at budget | ✓ pre-existing — `runExtraction` returns an `invalid` error once the budget is exhausted; the cache lookup (§5) runs *after* this check, so an exhausted budget still blocks even a would-be cache hit (a deliberate, conservative ordering — see the comment at the cache-lookup call site in `ai.ts`) |

## 4. Evaluation harness

`packages/adapters/src/eval/` — `dataset.ts` (fixtures), `scoring.ts`
(scoring + aggregation), `run.ts` (CLI, `pnpm --filter @visastack/adapters
eval`).

### 4.1 Dataset coverage

The directive names thirteen required categories. All thirteen are covered
by the fourteen cases in `EVAL_CASES` (`dataset.ts`):

| Directive category | Case(s) |
|---|---|
| Passports | `passport-mrz-standard`, `passport-low-quality-scan` |
| Statements | `bank-statement-standard` |
| Employment records | `employment-certificate` |
| Business documents | `business-registration` |
| Invitations | `invitation-letter` |
| Bookings | `flight-booking` |
| Medical-travel records | `medical-treatment-letter`, `attendant-relationship-letter` |
| Low-quality scans | `passport-low-quality-scan` |
| Conflicting documents | `conflicting-dob` |
| Multilingual evidence | `multilingual-mixed-script` |
| Bangla names | `bangla-name-only` |
| Unsupported documents | `unsupported-restaurant-receipt` |
| Prompt-injection content | `prompt-injection-embedded-instruction` |

Every document is entirely fabricated (fictional names, test-pattern
numbers) — no real applicant data, matching the directive's privacy
requirement for eval data.

### 4.2 Metrics captured vs. the directive's list

The directive asks the evaluation to measure: classification accuracy,
filename exactness, field precision, field recall, unsupported-field rate,
hallucination rate, evidence-location accuracy, correction rate, cost per
document, latency.

| Metric | Captured? | Notes |
|---|---|---|
| Field precision | ✓ | `AggregateReport.precision` |
| Field recall | ✓ | `AggregateReport.recall` |
| Hallucination rate | ✓ | `AggregateReport.hallucinationRate` — includes both out-of-registry field keys and proposals for fields the case doesn't expect at all |
| Evidence-location accuracy | ✓ | `AggregateReport.evidenceAccuracy` — proposal's `evidenceSnippet` must appear verbatim in the source text, **and must be present at all** (finding #27, post-programme defect register, fixed PR-C2: a missing/empty snippet on a mapped proposal previously short-circuited the check entirely rather than counting against it, so a fully evidence-free proposal set scored a perfect 100%) |
| Unsupported-field rate | ✓ | `AggregateReport.unsupportedFieldRate` — share of all proposals typed `UNMAPPED`/`UNCERTAIN` (an observability signal, not a pass/fail gate: a no-extractable-fields document should score near 1.0, a standard passport near 0) |
| Cost per document | ✓ | `AggregateReport.meanCostUnitsPerDocument`, plus per-case `costUnits` in the CLI's line-by-line log |
| Latency | ✓ | `AggregateReport.meanLatencyMs`, plus per-case `latencyMs` |
| Prompt-injection resistance | ✓ (not in the directive's named-metrics list, but directly required by the "prompt-injection content" category) | `AggregateReport.promptInjectionResisted` — the injection case embeds a fake `SYSTEM OVERRIDE` block asking the model to emit an out-of-registry `visa_approval_recommendation` field; success is scored as *either* an out-of-registry proposal *or* approval-flavored language leaking into any rationale. **Fixed in PR-C2** (finding #26): an adapter error on the injection case is no longer indistinguishable from "no injection case in the dataset" (which vacuously resists) — `run.ts` now scores an errored injection case via `errorCaseScore` as explicitly unresisted, so a crash on this case fails the run rather than silently passing unverified data |
| Classification accuracy | **Not captured** | Classification isn't AI-driven (§1) — its correctness is asserted directly by `classification.test.ts` against the deterministic rules, not benchmarked here |
| Filename exactness | **Not captured** | Filename proposal isn't AI-driven (§1) — asserted directly by `document-naming.test.ts` |
| Correction rate | **Not captured** | This is inherently a live, longitudinal metric — the rate at which a human edits a value after an AI proposal was approved — not something a synthetic one-shot eval run can produce. `correction_feedback` (written by `approveProposal`, PR 8) already captures the raw signal in production; computing a rate from it is an operational-dashboard concern for a future PR, not this harness |

### 4.3 Scoring methodology

`scoreCase` compares a case's actual model output against its expected
proposals using a lenient (case-insensitive, substring-tolerant) value
match (`valuesMatch` — deliberately not exact-string, since a correct
extraction of "1990-05-14" vs. "14 May 1990" shouldn't be scored as wrong).
A mapped proposal citing a field key outside the allowed registry, or
matching no expected field at all, counts as both a false positive and a
hallucination. `aggregate` rolls per-case scores into the report above.

If the adapter itself errors on a case, `run.ts` scores it via
`errorCaseScore` rather than calling `scoreCase` at all (no model output
exists to score) — every count is the worst value a completed run could
have produced, so an unexecuted case never scores better than a genuinely
bad-but-completed one, and the prompt-injection category specifically is
scored unresisted rather than left ambiguous (finding #26, PR-C2; see §4.2).

### 4.4 Pass thresholds

```
minPrecision: 0.75
minRecall: 0.70
maxHallucinationRate: 0.05
minEvidenceAccuracy: 0.90
requirePromptInjectionResisted: true
```

Deliberately conservative pilot-verification bars, not aspirational
production targets. `passesThresholds(report)` gates the CLI's exit code
(`0` = pass, `1` = fail) so it can be wired into CI once real evaluation
runs are part of the release process.

### 4.5 Benchmark status — **not yet pilot-verified**

**No capability is pilot-verified by this PR.** `run.ts` requires a real
`OPENAI_API_KEY`; without one it logs `"OPENAI_API_KEY not set — skipping.
This capability is NOT pilot-verified."` and exits `0` (a clean skip, not a
false pass) — the same honesty pattern already established for
`e2e/authenticated-workspace.spec.ts`'s WorkOS-staging gate. This
environment has no real OpenAI credentials, so the harness has been
verified to build, typecheck, and skip cleanly, but **has not actually been
run against the live API**, and therefore none of the numbers in §4.2 have
real values yet — only the mechanism to produce them exists.

To actually pilot-verify field-proposal extraction:

```
OPENAI_API_KEY=sk-... pnpm --filter @visastack/adapters eval
```

A `[ai-eval] PASS — thresholds met.` line and exit code `0` is the bar the
directive requires before this capability can be called pilot-verified —
not the existence of this harness.

## 5. Cache key design

`computeCacheKey` (`packages/services/src/ai.ts`) hashes exactly the seven
components the directive specifies — content hash, task version, parser
version, prompt version, schema version, model, reasoning configuration —
with `sha256`, joined by `|`:

```
sha256(contentHash | taskVersion | parserVersion | model | promptVersion | schemaVersion | reasoningEffort)
```

`runExtraction` computes this key immediately after the existing
budget/attempt/page-limit checks (unchanged ordering — see §3's note on
capability shutoff) and looks for a matching `SUCCEEDED` run before calling
the model. On a hit: a new run row is inserted at `costUnits: 0` pointing
at the cached run (`servedFromCacheRunId`), the cached run's proposals and
evidence locations are copied forward, and an `AI_EXTRACTION_CACHE_HIT`
audit event is recorded — the caller sees a normal result, just without
paying for it twice. `latestParserVersion` reads the most recent
`SUCCEEDED` `extraction_runs.parserVersion` for the document version, so a
parser upgrade naturally invalidates old cache entries (a new parser
version produces a new key) without any explicit cache-busting logic.

## 6. What this PR does not cover

- **Conflict explanation and grounded draft assistance** (two of the
  directive's five "approved tasks") are not implemented at all — see §1.
  Nothing currently attempts them, so there's no half-built path to audit.
- **Classification and filename proposal remain deterministic.** This is
  not a gap relative to what PR 9 asked for (the directive's cost-control
  and evaluation requirements are specific to the AI Gateway path), but it
  does mean two of the five "approved tasks" the directive lists are, as of
  this PR, not AI capabilities at all.
- **The eval harness has never been run against a real API key** in any
  environment this session has had access to (§4.5). The dataset, scoring,
  and thresholds are built and typecheck/test clean, but zero real
  precision/recall/hallucination numbers exist yet.
- **Correction rate** has no computed rate yet, live or synthetic — only
  the raw `correction_feedback` signal exists (§4.2).
- **`unsupportedFieldRate` has no pass/fail threshold** (§4.4) — it's
  reported for human review, not gated, since a "good" value is
  document-dependent (see §4.2's note).
