### 1.2 Test-suite defects found (not from GitHub review threads)

**D-T1 — Two pre-existing flaky timeouts, same root cause, not yet fixed
everywhere.** A prior commit on `main` (visible in Vercel deployment metadata
for `a8debb2d5`, "Fix CI-only timeout in commercial-readiness.test.ts's first
test") already diagnosed this exact pattern: a test file's *first* dynamic
`import('./…')` transitively pulls in `./ai` → the OpenAI SDK's esbuild
transform, which is fast in isolation but can exceed Vitest's 5000ms default
`testTimeout` under full-monorepo parallel contention. That commit fixed it in
`commercial-readiness.test.ts` and `providers.test.ts` but **missed two other
files with the identical shape**:

- `apps/web/src/lib/capabilities.test.ts` → `getPlatformCapabilities > reports
  every one of the 20 registry fields` (first test in the file) — timed out
  in both the initial baseline run and the `--continue` re-run.
- `apps/web/src/app/api/health/ready/route.test.ts` → `GET /api/health/ready
  … returns 200 "ready" when DB is connected+migrated and WorkOS config is
  present` — timed out only in the `--continue` re-run (order-dependent,
  exactly as the diagnosing commit's message predicted for `providers.test.ts`
  before it was fixed).

Not a security defect; a test-infrastructure gap. **Disposition:** both fixed
in PR-A (`docs/audits/post-programme-defect-register.md` retroactively
updated) — `health/ready/route.test.ts` reproduced this same flake in PR-A's
own `--force` full-suite verification pass after the Codex-feedback commit,
so it was fixed immediately alongside `capabilities.test.ts` rather than
deferred to the Phase 5 PR that also touches that file — by giving each file's first
test a generous explicit timeout, matching the existing fix's pattern.

**D-T2 — `turbo run test` aborts sibling packages on first failure.**
Discovered while reconciling test totals: the first baseline run (no
`--continue`) reported `ELIFECYCLE Test failed` for `@visastack/db`,
`@visastack/adapters`, and `@visastack/services` with **no test summary at
all** — not because those suites failed, but because Turbo killed their
still-running `vitest` processes the moment `@visastack/web`'s suite failed
(D-T1). This is a CI-hygiene risk: a single flaky test in one package can
mask a real regression in another package by preventing its summary from
ever printing. **Disposition:** not a defect in application code; noted here
so the Phase 6 CI PR considers `turbo run test --continue` (or per-package
`fail-fast: false`) so a flake in one package never hides a genuine
regression in another.

**D-T3 — PGlite fully serializes concurrent transactions regardless of
advisory-lock contention, limiting what a `Promise.all`-based "race" test
can actually prove in this suite.** Discovered while verifying (per this
programme's own non-vacuousness discipline: disable the fix, confirm the
regression test fails; restore, confirm it passes) round 8's fix for finding
#52 (PR-A, `packages/services/src/db.ts`'s `lockOnEmail` /
`pg_advisory_xact_lock`). A deterministic test that held one transaction's
lock for a fixed delay and asserted a second transaction genuinely blocked
on it passed identically whether or not the second transaction's code
actually took the lock. A temporary diagnostic (raced two transactions
against two *unrelated*, non-contending advisory-lock keys — no shared
resource at all) still showed full serialization: PGlite runs one
transaction's statements to completion before starting the next one's,
independent of any lock. This is a characteristic of PGlite's single-process,
in-process WASM execution model, not a bug in the lock code or in test logic.
**Implication:** a `Promise.all([opA(db), opB(db)])`-shaped test in this
codebase's suite generally proves "whichever operation's transaction is
dispatched first completes fully before the next one starts" — it does
**not** prove genuine interleaved, lock-arbitrated concurrency the way the
same code would behave against real concurrent Postgres connections (Neon
serverless in production). The underlying fixes this programme has shipped —
advisory locks (`AUDIT_CHAIN_LOCK_KEY`, `GRANT_LOCK_KEY`,
`EMAIL_LOCK_NAMESPACE`), partial unique indexes, `FOR UPDATE` row locks —
remain correct and necessary for production's real concurrent-connection
Postgres; only this test harness's power to empirically *prove* the
race-closure via true concurrent interleaving is limited. Where a test
still races the two real, full operations against each other (rather than
using artificial delays), its PASS remains meaningful evidence for the
**outcome contract** (no unrecoverable/duplicated state ever results,
whichever operation happens to run first) — just not, by itself, proof that
a lock specifically is what enforces it in every environment. **Disposition:**
not a defect in application code; documented so a future contributor doesn't
mistake a passing PGlite-based "race" test for proof of lock participation,
and doesn't spend time chasing a "flaky-looking" pass/fail pattern that is
actually this fully-serial execution model. The one test in
`pilot-access.test.ts` that relied solely on this false signal (a
fixed-delay "genuinely participates in the lock" test) was removed rather
than kept as misleading evidence; the surviving race test against the real
operations plus direct code review of `lockOnEmail`'s Postgres semantics
carry the correctness claim instead. No action needed for the Phase 6 CI PR
beyond awareness — a real cross-connection concurrency proof would require
pointing tests at a real Postgres instance, which is out of scope for the
zero-paid-stack constraint this programme operates under.

**D-A1 — `purgeExpiredDocuments` has no dedup/idempotency check against
already-queued erasure jobs, so re-running it on the same still-eligible
document can enqueue duplicate jobs for the same storage object.**
Discovered during self-review of PR-B2's finding #13 fix. `purgeExpiredDocuments`
(`packages/services/src/retention.ts`) re-derives its candidate set from
`documentsPastRetention` (retention window elapsed, not held) every time it
runs, and `enqueueErasureJob` is a plain `INSERT` with no check for an
already-active job on the same `storageObjectId`. This gap predates PR-B2 —
even before finding #13's fix, running retention purge twice in quick
succession on the same document (before the erasure worker had a chance to
run) could already enqueue duplicate jobs. PR-B2's fix widens the window in
which this is reachable: a document now deliberately survives (per finding
#13) until *every* sibling storage-object job is `VERIFIED`, rather than
being deleted (and so no longer matching `documentsPastRetention` at all)
after the first. A document with one permanently stuck sibling (`FAILED` or
`BLOCKED_BY_HOLD`) now stays purge-eligible-looking for much longer, so a
human re-clicking the (manual-only, not cron-triggered) "run retention
purge" admin action on it is more likely to hit this gap than before.
**Originally assessed impact (round 1): low** — reasoned that
`finalizeVerifiedJob`'s sibling-count check was "naturally robust to
duplicate rows... with no risk of... a further-delayed document deletion,
not an incorrect one." **This was wrong, and Codex round 5 proved it**:
the original check was `siblings.every(status === 'VERIFIED')`, a check
over every JOB ROW, not every unique storage object. A duplicate job that
independently reaches `FAILED` (exhausted retries — ordinary, not
exotic; any job can end up there) blocks that `every()` forever, even
though the real, unique storage object it redundantly targets already has
a *different* row sitting at `VERIFIED`. That is exactly "an incorrect
one" (permanently blocked, not merely delayed) — the round-1 assessment
missed that a redundant row's own failure is a completely ordinary,
expected occurrence, not a rare edge case.

**Fixed (partially) in PR-B2 round 5:** `finalizeVerifiedJob`'s completion
check now groups siblings by DISTINCT `storageObjectId` and requires every
unique object (not every row) to have at least one `VERIFIED` job —
`erasure.ts`, see finding #13's own entry below. This closes the
correctness gap (a document can no longer be blocked forever by a
redundant row's failure) by construction, regardless of how or why a
duplicate row arose — without needing to prevent duplicates from being
created at all. **Still deferred to PR-C1:** preventing the duplicate
*enqueueing* itself (an existence check against already-active jobs for
the same `storageObjectId` before inserting, or a partial unique index) —
now a pure efficiency/hygiene concern (avoiding wasted worker attempts and
extra rows), not a correctness one, since finalization no longer depends
on avoiding duplicates. Still a distinct piece of work from PR-B2's own
invariants and still scope creep on this PR; candidate for PR-C1
(processing job fencing and idempotency), which is already about exactly
this class of gap for the other job queue in this codebase.

## 3. PR #64 preview-deployment investigation

**Distinguishing the failed preview from the successful merge deployment.**
Every commit pushed to the PR-#64 head branch
(`claude/visastack-commercial-readiness-an08tb`) produced a Vercel **preview**
deployment in `ERROR` state; the merge-to-`main` deployment for the *same*
final commit (`a8debb2d5`) succeeded normally
(`dpl_Gpd4ViGNaz5pSprveXCKwpWDGM5m`, `READY`).

Direct evidence pulled for the preview build of the exact final pre-merge
commit (`dpl_2Y2TfaRgrJZdY1Fgt2RHd7t8Divy`, commit `a8debb2d5`):

- `errorCode: "BUILD_FAILED"`, `errorMessage: "Resource provisioning failed"`.
- `get_deployment_build_logs(errorsOnly: true)` → **"No error/stderr/exit
  events in this build."**
- `buildingAt` → `ready` spans **~1.7 seconds** — the build container never
  actually started; this fails before any install/build step runs.

This is not an isolated incident: the same signature (instant
`BUILD_FAILED`/`Resource provisioning failed`, zero log lines, preview-only,
**never** the corresponding production deployment for the same final commit)
recurs identically across every one of PRs `#58`–`#64` (7+ distinct preview
builds, across multiple separate days). **Conclusion: this is conclusively
not a code defect** — the build never reaches a point where VisaStack's own
code could be at fault. The most evidence-consistent explanation, given the
project sits on Vercel Hobby (which enforces a single concurrent-build slot)
and this account's team runs 6 total projects
(`visastack`/`travelrouter`/`tradeproof`/`peopleops2025`/`flowtal`/`bidesh365`)
that can compete for that same slot, is a Hobby-tier build-concurrency
ceiling — but this session did not have direct access to Vercel's
account-level concurrency/plan-limit dashboard to prove the exact mechanism
with certainty, so that specific cause is stated as the best-supported
hypothesis, not a proven fact. What **is** proven: the production/deployed
artifact users and reviewers actually see has never been affected by this —
every `main` merge deployment for `#58`–`#64` reached `READY` normally.
**Disposition:** no code change required; documented here so future preview
`ERROR` states on this repo are correctly triaged (check `get_deployment_build_logs`
before assuming a code regression) rather than re-investigated from scratch
each time.

**Reconfirmed repeatedly on PR #65** (this programme's PR-A, merged as
`45043dd`): the identical signature —
`errorCode: "BUILD_FAILED"`, `errorMessage: "Resource provisioning failed"`,
zero build-log lines, `buildingAt`→`ready` span ~1–2 seconds — recurred on
essentially every one of PR-A's ten commits across its nine Codex review
rounds (first directly confirmed via `get_deployment_build_logs` on commit
`a9c85df55cfcfadc9b648fe1379309b2be6e024e`, `dpl_8VYgttz39guZAF3F7GfWsvdoQni3`;
every subsequent occurrence matched that exact signature closely enough,
including timing, that it was triaged by pattern-match against the confirmed
instance rather than independently re-fetched from Vercel each time —
consistent with the triage rule above, and never once correlated with an
actual code regression: PR-A's own GitHub Actions "Lint · Build · Typecheck ·
Test" run was green on every commit where this preview failure also
appeared). **Disposition unchanged:** no code change required; the pattern is
now established across two full PRs' worth of commits (#64 and #65) and
should be triaged the same way — by pattern-match, not by re-investigation —
for the remainder of this program's PRs unless the *signature itself*
changes (a different error code, non-trivial build-log output, or a failure
that also shows up on the GitHub Actions "Lint · Build · Typecheck · Test"
