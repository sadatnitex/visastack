Investigated in depth (not merely surfaced):

## 7. Known-defect verification (new directive §4) — confirmed against actual code, not assumed

Every function named in the directive's "Current reality" section was read in full. Verdicts:

### Tenant isolation and authorization

| Claim | Verdict | Evidence |
|---|---|---|
| `addNote()` lacks mission-level authorization | **CONFIRMED — no auth check at all.** | `packages/services/src/agency.ts:121-152`. The only validation is a non-empty body. Any authenticated account can write a note onto any `missionId` via the server action (`agency/[orgId]/actions.ts:121-134`, which reads `organizationId` from the form but never checks it). The UI never *offers* a foreign mission id, but the server action itself has no independent check — a direct POST bypasses it entirely. |
| `assignMember()` doesn't prove assignee org membership | **CONFIRMED.** | `agency.ts:23-61`. Checks `isOrgAdmin(actor, organizationId)` on entry, but never verifies `memberAccountId` actually has a `memberships` row for that org — any existing account id can be "assigned." |
| `assignMember()` doesn't prove org has current access to the mission | **CONFIRMED.** | Same function — never checks `missionId` against `listMissionsForOrganization`'s reachable set. An org admin can create assignment records against any `missionId` UUID in the system, including applicants who never granted the org anything. Bounded impact: per the code's own comment, "assignment... never by itself grants record access — that is always a grant," so this is a data-integrity/enumeration issue, not a direct read of applicant data. |
| `requestEvidence()` doesn't prove an active accepted grant covers the applicant | **CONFIRMED.** | `agency.ts:159-216`. Checks `isOrgAdmin` + field-shape validation + a real rate limit (20/hr), but never checks `applicantId` against any grant naming the organization. Any org admin can raise a request against any applicant UUID; the applicant sees it in their inbox with no prior relationship. Mitigated only by UUID unguessability and the rate limit. |
| `listMissionsForOrganization()` doesn't filter grant status/acceptance/expiry | **CONFIRMED, and broader than stated.** | `agency.ts:101-118`. The function itself takes a bare `organizationId` with **no actor parameter at all** — it is safe today only because its one call site (`agency/[orgId]/page.tsx`) happens to check `isOrgAdmin` first. A footgun for any future direct caller, not merely a filtering gap. |
| `setMembershipActive()` authorizes against one org but updates by membership ID alone | **CONFIRMED — the most serious finding of this pass.** | `packages/services/src/organizations.ts:308-341`. `isOrgAdmin(actor, organizationId)` is checked, but the `UPDATE` itself filters **only** by `memberships.id = membershipId`, with no `AND organization_id = organizationId`. Any org admin (including one who just self-registered a fresh org — `createOrganization` has no gate) can deactivate or reactivate **any account's membership row in any other organization**, given only its UUID (which is rendered client-side and posted back verbatim by `member-toggle-button.tsx`). This is a genuine cross-tenant IDOR — a hostile org can silently strip a competitor's staff access or undo a legitimate offboarding. |
| Owner/last-owner safeguards are missing | **CONFIRMED by omission.** | No code path in `organizations.ts` checks "is this the last active OWNER" before deactivation; `setMembershipActive` has no role-comparison logic between actor and target at all. |
| `bulkExport()` fabricates an ADMIN policy actor | **PARTIALLY CONFIRMED — more nuanced than stated.** | `agency.ts:369-450`. It does check `isOrgAdmin` on entry and re-evaluates the real `authorize()` policy engine **per applicant** afterward (only applicants who granted `EXPORT_PROFILE` to this org are included; everyone else is silently skipped) — this is **not** a cross-tenant data leak. However, it constructs a synthetic `Actor` with a **hardcoded `role: 'ADMIN'`** rather than the actor's real membership row, which is exactly the pattern the directive's PR 2 explicitly wants replaced with "the actor's real membership role." |
| `bulkExport()` hardcodes `stepUpSatisfied: true` | **CONFIRMED, literally.** | `agency.ts:411`. Since `EXPORT_PROFILE` is in `STEP_UP_ACTIONS` (`packages/policy/src/authorize.ts:33-37`) and no step-up flow exists anywhere in the app, this hardcoded `true` **silently bypasses the step-up gate on every bulk export**. Directly violates the directive's own "Never hardcode `stepUpSatisfied: true`" rule. |
| `bulkExport()` loses mission/category/document grant scopes; can export more than authorized | **NOT REPRODUCED as literally stated** — the function does correctly re-check the full policy decision per applicant and only includes granted applicants — **but is still gated off in PR 1** because of the two confirmed items above (fabricated role, hardcoded step-up), consistent with the directive's explicit instruction to disable bulk export "until repaired" regardless of exact severity, and because it has not been rebuilt "from first principles" per PR 2's mandate. |

Functionally enforced at the access-check layer; not reflected in persisted state — exactly "insufficiently governed," not "unenforced." |

## 12. PR 1 scope decisions and rationale (capability registry design)

Given §7's verdicts, PR 1 implements the registry with these controlled-pilot values, each derived from actual verified state rather than hardcoded blindly wherever the underlying signal is environment-driven:

- **Gated to `disabled` in controlled pilot, pending PR 2:** `agencyCollaboration` (covers `addNote`, `assignMember`, `requestEvidence`, `setMembershipActive` — the four confirmed authorization gaps, one of which is a genuine cross-tenant IDOR) and `bulkExport` (confirmed hardcoded step-up bypass + synthetic role). These are gated at the server-action/route layer, not merely hidden in the UI, per the directive's explicit "no unsafe feature may merely disappear silently" — each returns a clear, honest, non-security-detail-leaking message.
- **Left `available`:** direct individual-to-individual `sharing` (accept/revoke/pause, category/document scoping, and the live per-request re-authorization added in the Collaboration PR are real, tested, and not among the confirmed cross-tenant defects — the confirmed grant-state-machine gaps are owner-self-service integrity issues, not authorization breaches, since only the applicant owner can trigger them on their own resource); `documentUpload`, `manualProfile`, `missionWorkspace`, `packGeneration`, `deterministicExtraction`, `ownerPreview` (the `safetyStatus` gap found in §7 does not cross a tenant boundary — owner previewing their own unscanned document — and its fix is explicitly PR 3 scope; flagged, not silently left, in this document and in code comments), `authentication`.
- **Reported `disabled`/`unconfigured` reflecting pre-existing reality, not new restriction:** `thirdPartyPreview`, `originalDownload`, `redactedDownload` (all already fail-closed by design per the existing baseline — the registry now makes this truthful and visible rather than invisible), `malwareScanning` (structural-only scanner is explicitly not this capability), `payments` (no provider exists), `publicSignup` (no application-level allowlist exists; WorkOS Staging itself currently has exactly one user, but this is not a technical guarantee — flagged), `realApplicantData` and `commercialClaims` (policy-level flags the banner and future copy-review reads from).
- **`aiExtraction`:** computed from real env presence (`AI_ENABLED`/`OPENAI_API_KEY`), not hardcoded — currently unconfigured in this deployment, matching the existing baseline's own statement that AI is "fully inert... off by default."
