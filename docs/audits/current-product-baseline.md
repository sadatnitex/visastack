A direct, page-by-page read of every route in `apps/web/src/app` (not a generic checklist) found one systemic, pervasive defect: nearly every mutation button in the app — revoke access, pause/resume a grant, release a legal hold, retry a failed job, verify/reject an organization, deactivate a member, respond to an evidence request, open/approve/publish a pack version, advance or snapshot a mission, grant/revoke consent, add an applicant — was a plain `<form action={...}>` bound to a `Promise<void>` server action. If the underlying service call returned an error, the user saw **nothing** — no message, no changed state, just an apparent no-op. Only a couple of forms (e.g. the retention-purge button) had ever gotten the correct `useActionState` + inline-message treatment. Fixed **all** of them, consistently, using that one correct existing pattern as the template — not a partial sample. Also fixed: two real, missing-`<label>` accessibility defects on the workspace dashboard's "Add applicant" form (only a `placeholder`, no `<label>`); added `window.confirm()` before the destructive actions that lacked it (revoke access, release legal hold, deactivate a member, cancel a mission, publish a pack version) matching the confirm-before-destructive convention already established elsewhere; and fixed a silent failure in document preview (redirected nowhere, showed nothing, if the signed URL couldn't be issued) with a proper error banner. No schema/migration change; no new domain capability — this is UI-layer correctness only.
**Production deployment:** `visastack-five.vercel.app` — Vercel project `prj_RZcDRy1odwehHuDqsiGwvVGC0epe`. PRs #40–#51 are merged and live in production. This round's work is **new, typecheck/build/lint clean, not yet deployed**.

From `.env.example` and `docs/governance/service-wiring.md`:

- **Database (required, first present wins):** `DATABASE_URL` · `POSTGRES_URL` · `DATABASE_URL_UNPOOLED` · `POSTGRES_URL_NON_POOLING` · `POSTGRES_PRISMA_URL`.
- **Signed blob storage (required for document preview/download):** `BLOB_SIGNING_SECRET` — consumed by `/api/blob/[key]` and both storage backends. *Fixed: now in `.env.example`.*
- **Object storage backend (Release B):** `BLOB_READ_WRITE_TOKEN` — when present, `createStorage()` selects `VercelPrivateBlobStorage` (real private access); when absent, falls back to `NeonBlobStorage` (reduced-control) in local dev/tests/PR previews, but **fails closed (throws) in production** (`VERCEL_ENV === 'production'`) rather than silently degrading — fixed this round.
- **Upload quotas (optional overrides):** `QUOTA_MAX_UPLOAD_MB`, `QUOTA_MAX_APPLICANT_EVIDENCE_MB`, `QUOTA_MAX_ACCOUNT_EVIDENCE_MB`, `QUOTA_PLATFORM_WARNING_MB`, `QUOTA_PLATFORM_HARD_STOP_MB` — conservative pilot defaults (10/50/100/500/700 MB) apply when unset.
- **Async intake sweep (optional; this round):** `CRON_SECRET` — authorizes the periodic `/api/jobs/process-intake` sweep (Vercel Cron). Absent → the route fails closed (503); uploads still enqueue and process via the immediate post-upload trigger regardless, so this only gates the durability backstop, not the common path.
- **AI Gateway (Release D, wired this round):** `AI_ENABLED` (must be exactly `'true'`; absent = feature fully off regardless of any other AI var), `AI_PROVIDER` (unset or `'openai'` — anything else disables the feature; no other provider adapter exists), `OPENAI_API_KEY` (required alongside `AI_ENABLED`), `OPENAI_MODEL_PRIMARY` (defaults to `gpt-5.6-terra`), `OPENAI_PROJECT_ID` (optional, sent as the `OpenAI-Project` header), `OPENAI_REASONING_EFFORT` (optional, forwarded as the Responses API `reasoning.effort` param), `OPENAI_STORE_RESPONSES` (must be exactly `'true'` to opt in; defaults to `false` — privacy minimization, master directive §8), `AI_PILOT_MONTHLY_HARD_LIMIT_USD` (platform-wide spend cap, default $20), `AI_PER_DOCUMENT_LIMIT_USD` (per-document spend cap, default $0.50), `AI_MAX_ATTEMPTS` (optional cap on AI invocations per document), `AI_MAX_PAGES_PER_DOCUMENT` (optional cap using the deterministic extractor's recorded page count). USD caps are converted to the service layer's token-based "cost units" via a documented, deliberately-conservative approximate rate (`apps/web/src/lib/ai.ts`) — an honest approximation for budget-gating only, not a billing source of truth.
- **Declared but not yet wired (future phases):** `SENTRY_*`. `STORAGE_*` (S3-compatible) is an optional future migration path, not required now that Vercel Private Blob is wired. `INNGEST_*` has been removed from the env contract — intake processing uses a DB-backed job queue instead (master directive §5: Inngest is not on the approved-infra list).

## Known defects

**P0 — resolved in PR #40 (merged, production-verified)**
- **Preview served original bytes under a "redacted" label.** `/api/blob/[key]` returned the stored original bytes for any valid token regardless of the signed `variant`; `previewDocument` minted a `redacted` variant for everyone. *Fixed:* the serving route fails closed for any non-`original` variant (HTTP 501), and `accessDocument` mints an `original` preview only for the applicant owner; third parties get `redacted`.
- **Identity keyed by mutable email**, not the immutable WorkOS user id. *Fixed* — `workos_user_id` binding (migration `0010` + `provisionAccount` rewrite + 6 tests); email is now mutable contact data. Follow-up still open: make the column NOT NULL after all live users are bound.

**P1 — resolved in PR #51 (Mission PR, merged, production-verified)**
- **Mission readiness silently ignored unresolved fact conflicts.** `computeReadiness` (`packages/services/src/missions.ts`) considered a FIELD requirement satisfied whenever the applicant had *any* current fact version for that key — including one flagged `CONFLICTED` by `approveProposal` (AI Gateway PR), meaning an active, unresolved disagreement between an AI proposal and an already-trusted value was completely invisible to mission readiness. Build Spec §4.5 defines readiness as coverage **and** validity/consistency, not coverage alone. *Fixed:* a `CONFLICTED` current fact version no longer counts as satisfying its requirement; the `missing` list now carries a `reason: 'unresolved_conflict'` (vs. `'not_provided'`) so the UI can tell a reviewer "this was provided but is disputed" apart from "this was never provided." 1 new test.

**P1 — resolved this round (UI Correctness pass, not yet deployed)**
- **Nearly every mutation button in the app gave zero feedback on failure.** A direct audit of every page found this was not an isolated bug but the *default* pattern: revoke/pause/resume a grant, release a legal hold, retry a failed job, verify/reject an organization, deactivate a member, respond to an evidence request, open/approve/publish a pack version, advance or snapshot a mission, grant/revoke consent, and add an applicant were all plain `<form action={...}>` bound directly to a `Promise<void>` server action. If the underlying service call returned `Result.err` (forbidden, not found, invalid state), the form simply re-rendered with no visible change and no message — indistinguishable from "nothing happened" to the user. Only the retention-purge button (`purge-button.tsx`) had the correct `useActionState` + inline `field-msg` + `window.confirm()` pattern. *Fixed:* converted every one of the actions above to return `ActionState` (`{ok, message}`) instead of `void`, and built one small client wrapper component per surface (`action-buttons.tsx`, `pack-version-buttons.tsx`, `member-toggle-button.tsx`, `grant-op-buttons.tsx`, `respond-buttons.tsx`, `mission-buttons.tsx`, `consent-button.tsx`) using `useActionState` to show the real result — success or the actual service error message. Added `window.confirm()` to the destructive actions that lacked it (revoke access, release legal hold, deactivate a member, cancel a mission, publish a pack version), matching the confirm-before-destructive convention the purge/deletion buttons already established. No behavior changed for the success path — only the previously-silent failure path now surfaces.
- **Two accessibility defects on the workspace dashboard's "Add applicant" form.** The name `<input>` had only a `placeholder` (not a substitute for a label) and the relationship `<select>` had no associated label at all. *Fixed:* extracted into a new `add-applicant-form.tsx` with real `<label htmlFor>` elements for both fields, reusing the existing `field-label`/`input` classes already used correctly elsewhere (e.g. `grant-form.tsx`).
- **Document preview failure was silent.** `previewDocumentAction` redirected to the signed preview URL on success but did nothing at all if `previewDocument` failed (e.g. a race on document state) — the click appeared to do nothing. *Fixed:* falls back to redirecting to the applicant page with a `?preview_error=1` banner (same `notice notice-warn` pattern the landing page already uses for a failed sign-in).

### Follow-up fix this same round: two real defects found by automated PR review (PR #47, `chatgpt-codex-connector[bot]`)

The initial `looksLikePlainText()` heuristic (above) had two genuine bugs, both fixed before merge:

1. **P1 — stored XSS via spoofed content type.** The heuristic accepted *any* clean-UTF-8, control-character-free byte content as "safe text" regardless of the object's declared `contentType`. HTML and SVG source are both ordinary UTF-8 text with no control characters — structurally indistinguishable from a real TXT/MD file by content alone. A caller that bypasses the browser file picker (a direct Server Action call, which is not gated by the `accept` attribute) could declare `contentType: 'text/html'` or `'image/svg+xml'` with actual `<script>` payloads, have the scanner mark it `safe`, and have `/api/blob/[key]` later serve it `inline` under the app's own origin — real stored XSS (HTML execution or SVG script execution). **Fix:** gated the plain-text path to an explicit allow-list, `PLAIN_TEXT_CONTENT_TYPES = {'text/plain', 'text/markdown'}` — an upload declaring `text/html`/`image/svg+xml`/anything else is rejected regardless of byte content. Also added `X-Content-Type-Options: nosniff` to `/api/blob/[key]`'s response headers as defense in depth against browser MIME-sniffing.
2. **P2 — UTF-8 truncation false negative.** The original heuristic decoded only a fixed-size byte prefix, which can split a multi-byte UTF-8 sequence exactly at the cut boundary and wrongly reject a perfectly valid non-ASCII text file larger than the sample size. **Fix:** decode the whole (already size-bounded, ≤25 MiB) byte array instead of a truncated sample.
3. **Tests** — 2 new cases added to `packages/adapters/src/adapters.test.ts`: spoofed `text/html`/`image/svg+xml` content rejected despite clean bytes (stored-XSS regression), and a >8KB file with a multi-byte CJK character straddling the old sample boundary now accepted (truncation regression). Full adapters suite: 28/28 passing.
4. This baseline audit, updated to reflect the above truthfully.

## Changes made this round (Collaboration PR — Release G, `claude/visastack-collaboration-release-g`)

1. **`packages/policy/src/types.ts` + `authorize.ts`** — new `individual_recipient` Actor kind fixing the P0 defect above (see "Known defects"). `documents.ts`'s `actorAudit` switch updated to match (TypeScript's exhaustiveness check caught the one call site that needed it). 5 new tests in `authorize.test.ts`.
2. **Schema (migration `0014`, additive-only)** — `grants.document_ids` (`uuid[]`, nullable): the policy engine's `Grant.documentIds` has existed in `packages/policy/src/types.ts` since the sharing feature was first built, but the column to persist it never did. `createGrant`/`CreateGrantInput` now accept and store it.
3. **`packages/services/src/sharing.ts`** — `loadGrants` (previously a private helper duplicated nowhere, living in `documents.ts`) moved here and renamed `loadGrantsForPolicy` (exported, reused by both `documents.ts` and the new function below — one source of truth for mapping grant rows into the policy engine's shape). New `getRecipientWorkspace(db, {actorAccountId, grantId})`: resolves the correct `Actor` (an `individual_recipient` for a direct grant, or a real `organization_member` with a live-fetched `Membership` for an org-mediated one — refusing anyone else), then re-evaluates `authorize()` **live, per resource** — `VIEW_METADATA` for every profile fact, `PREVIEW` for every document — using the grant's own `purpose` as the auth context. A field's category is its Release F pack (`field_definitions.packId`, populated this round — see below); a document's category is its classified `docType` mapped into the same pack vocabulary (`PASSPORT`/`BANK_STATEMENT` → `universal`, `EMPLOYMENT_CERTIFICATE` → `professional`), so one grant's `categories` allow-list scopes both consistently. Nothing here is a cached accept-time snapshot — revoking a grant blocks the very next call (tested).
4. **`apps/web/src/app/app/applicant/[id]/actions.ts`** — `saveFactAction` now passes `packId: def.pack` to `registerFieldDefinition`, populating the `field_definitions.packId` column the schema already had but nothing had ever written to (Release F's own field registry supplied the vocabulary; this round is what actually reads it back out for authorization).
5. **UI** — `grant-form.tsx` gains pack checkboxes (`categories`) and a per-document checkbox list (`documentIds`) so an owner can actually scope a grant narrower than "everything," not just pick actions/purpose/expiry. New `apps/web/src/app/app/shared/[grantId]/page.tsx` — the actual permission-filtered recipient workspace: shows the applicant's name, the grant's purpose/expiry, every field/document the live `authorize()` re-check allows, and an honest note when mission-scoping or document preview aren't available yet (rather than a silent blank page or a preview button that would just 501). `/app/shared/page.tsx` links to it from each `ACTIVE` grant row.
6. **Tests** — 14 tests in `sharing.test.ts`'s new `getRecipientWorkspace` suite: the primary direct-recipient path end-to-end (deny-before-accept → allow-after-accept), a stranger denied, an org-mediated recipient allowed via a real membership, a deactivated membership losing access, category scoping, `documentIds` scoping, mission-scope fail-closed behavior (with a real `missions` FK row, not a fake id), and immediate revocation. Full monorepo run: **142 service-package tests, 29 policy tests** — all passing.
7. **Known, honestly-scoped-out gap:** `listGrantsForRecipientAccount` only lists direct-account grants — an org-mediated recipient still has no "shared with your organization" discovery/accept inbox UI, even though `acceptGrant`/`getRecipientWorkspace` both already support and test that path. Agency Desk itself (assignments/notes/evidence requests/bulk export, built in PR #44) is unchanged this round.

## Changes made this round (Mission PR — Release H, `claude/visastack-mission-release-h`)

1. **`packages/services/src/missions.ts` — conflict-aware readiness.** `computeReadiness` now loads each fact key's current-version `status` (`loadFactStatusByKey`) instead of only checking presence; a `CONFLICTED` status no longer satisfies its requirement. `MissingRequirement` gained a `reason: 'not_provided' | 'unresolved_conflict'` field so a reviewer can tell "never given" apart from "given but disputed." No schema change — `CONFLICTED` has been a real, already-produced `FactStatus` (AI Gateway PR's `approveProposal`) that this function simply never checked.
2. **`packages/services/src/missions.ts` — requirement mapping + pack production.** New `buildRequirementMapping` resolves each of a pack version's requirements to the specific fact value (FIELD) or document(s) (DOCUMENT) satisfying it, reusing data already loaded by `snapshotMission` (no extra queries beyond the one pack-requirements fetch). `snapshotMission`'s persisted `content` now includes `requirementMapping`; once a mission has reached `READY_TO_EXPORT`/`LOCKED`/`CLOSED`, that snapshot *is* the application packet (Build Spec §4.5's "pack production") — the same immutable, checksummed artifact already built for evidence capture, not a new table or concept.
3. **New `getMissionSnapshot`** (owner-scoped, single-snapshot fetch by id) — snapshots were previously only listable in bulk (`listMissionSnapshots`), with individual content unreachable outside the DB.
4. **UI — snapshot detail + download.** New `/app/mission/[id]/snapshots/[snapshotId]` page renders the requirement mapping (satisfied/not, citation, backing value or document names), facts, and documents captured at that snapshot, plus a "Download JSON" link to a new owner-gated `.../download` route (mirrors the existing Pack Studio manifest-download route's pattern: serves the exact stored content, never regenerated). Mission page's snapshot list now links each row to its detail page and badges any snapshot taken at `READY_TO_EXPORT`/`LOCKED`/`CLOSED` as "Application packet" vs. plain "Working snapshot." Readiness's missing-requirements list now shows a distinct "Needs attention · disputed value" badge for `unresolved_conflict` entries instead of a generic Field/Document badge.
5. **Deliberately not built this round** (see Known defects/P2 above for the honest reasoning on each): a reviewer decision layer for individual requirements (request info / accept evidence / flag contradiction / record rationale); grounded letters/translations generation; mission-scoped evidence requests; wiring the dormant `documents.expires_at` column into readiness (no capture UI exists yet, so there is no real data to check against).
6. **Tests** — 2 new `missions.test.ts` cases (conflict-aware readiness denies satisfaction; requirement mapping correctly resolves field/document evidence and round-trips through `getMissionSnapshot`). Full monorepo run: **144 service-package tests** (up from 142), all packages typecheck/build/lint clean, `pnpm audit --prod --audit-level high` clean.
7. This baseline audit, updated to reflect the above truthfully.
