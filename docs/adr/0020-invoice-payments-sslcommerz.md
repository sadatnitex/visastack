# ADR-0020: Invoice payments: one hosted Bangladesh gateway plus verified manual payments

- **Status:** Accepted (architecture freeze, 26 Oct 2026); implementation pending (Sonnet packages S10 to S12, then S17 to S19). Merchant activation is an owner gate.
- **Date:** 2026-10-26
- **Deciders:** Owner (26 Oct 2026 instruction: invoice-by-invoice, one Bangladesh hosted gateway such as SSLCOMMERZ behind a provider port, manual fallback, the browser redirect never counts as proof); architecture session
- **PRD/Spec link:** `packages/services/src/billing.ts`, `plans.ts`, `ports.ts` (`PaymentPort`); `docs/roadmap/SMALL-COMMERCIAL-V1.md`

## Context

Verified on main `174ae1a`:

- Plans, subscriptions, scheduled downgrades, entitlements and billing accounts (`TRIAL, ACTIVE, GRACE, SUSPENDED, CLOSED`) exist. Invoices belong to an **organization** (agencies), never to a traveller, and are created by platform staff (`createInvoice`, platform owner plus step-up).
- `invoices` keeps `invoiced_amount_minor_units`, free-text `currency`, `status` (`OPEN, PARTIALLY_PAID, PAID, VOID`) and one running `collected_amount_minor_units` with the **latest** payment reference and date. There is no payment ledger. Database checks keep collected at or below invoiced.
- `recordInvoicePayment` (platform owner, step-up) adds an amount, does not check currency, has no idempotency by design, writes `INVOICE_PAYMENT_RECORDED` and the `CASH_COLLECTED` product event, and never changes the billing account status.
- `PaymentPort` is a stub (`NullPaymentPort` throws). Readiness reports payments unconfigured. Agencies cannot see their invoices; only `/app/admin/organizations/[orgId]` lists them.
- Signed webhooks follow the Resend pattern: raw body, verify, 401 on bad signature, idempotent apply.
- The SSLCOMMERZ developer documentation hosts did not resolve from the architecture session's network. The provider details below follow the v4 integration as widely documented (session API, IPN, Order Validation API, Transaction Query API) and **must be checked against the official v4 documentation when S11 is built**.

## Decision

### Scope

- Payers are agency organizations paying their own invoices. Travellers have no invoices in V1.
- Online payment covers invoices in **BDT**. Other currencies use the manual path only.
- One online attempt pays the **whole outstanding balance** at the moment it starts. Partial payments happen only through the manual path or admin recording.
- First release (S10 to S12): invoice-by-invoice online and manual payment. Then, in this same programme (owner, 26 Oct 2026: payments are built now; only security and compliance are deferred), the "Phase 2" section below: recurring period invoices, reminders, overdue handling, automatic reactivation, refunds, a second provider, receipt upload and an accounting export.
- Deferred as compliance: a tax engine (VAT and withholding rules) and statutory invoice formats. Invoices carry no tax lines until the owner and an accountant define them.

### Data (one migration, additive)

- `invoice_payments`: the cash ledger. One row per amount actually received or reversed: `invoice_id`, `amount_minor_units` (positive; a future `REFUND` kind is negative), `currency`, `kind` (`ONLINE`, `MANUAL_CLAIM`, `ADMIN_RECORDED`, and from S18 `CREDIT` and `REFUND`; create the enum with all five in S10 so S18 needs no enum change), `source_id` (the attempt, claim or null for admin), `provider` and `provider_transaction_id` (nullable), `reference`, `collected_date`, `recorded_by_account_id` (null for provider-verified), `created_at`. **Unique `(kind, source_id)`** and **unique `(provider, provider_transaction_id)`**: a second recording of the same money is impossible at the database level.
- `payment_attempts`: `invoice_id`, `organization_id`, `provider`, `merchant_tran_id` (unique, generated by VisaStack, never reused), `amount_minor_units`, `currency`, `status`, `provider_session_key`, `provider_val_id` (unique when set), `bank_tran_id`, `risk_level`, `last_provider_status`, `initiated_by_account_id`, timestamps, `recorded_at`.
- Attempt status: `CREATED → REDIRECTED → (VALIDATED → RECORDED) | FAILED | CANCELLED | EXPIRED | HELD_FOR_REVIEW`. `EXPIRED` may still move to `VALIDATED` if the provider later reports success (late success). `HELD_FOR_REVIEW` is for risky or unappliable money (see below).
- `manual_payment_claims`: `invoice_id`, `organization_id`, `submitted_by_account_id`, `method` (`BANK_TRANSFER, BKASH, CHEQUE, OTHER`), `reference`, `amount_minor_units`, `currency`, `paid_on`, optional short `note`, `status` (`SUBMITTED, APPROVED, REJECTED`), `decided_by_account_id`, `decided_at`, `decision_reason`. An optional receipt file is added in S12: it goes through the normal upload, quarantine and scan pipeline as an organization-owned billing file (`billing_receipts`: `claim_id`, storage object, scan status), visible only to the agency's owners and admins and to platform billing staff, and never attached to any traveller record.
- `invoices.collected_amount_minor_units` stays and becomes the **sum of the ledger**, updated in the same transaction as each ledger row while the invoice row is locked (`FOR UPDATE`). `collected_date` and `payment_reference` keep meaning "latest", as today.
- Every new code path tolerates the new tables being missing (migrations run after deploy): the features report "not available yet", never a crash.

### One recording function

`applyInvoiceCollection(tx, { invoiceId, amountMinorUnits, currency, kind, sourceId, provider?, providerTransactionId?, reference, collectedDate, recordedByAccountId? })`, used by every path:

1. Lock the invoice row. Refuse `VOID`.
2. Refuse if `currency` differs from the invoice currency (case-insensitive ISO code).
3. If the amount exceeds the outstanding balance, refuse with `exceeds_outstanding` (the caller decides what that means; see below).
4. Insert the ledger row (unique keys make a replay a no-op: on conflict return the existing row as "already recorded").
5. Update collected total and status (`PARTIALLY_PAID` or `PAID`), audit `INVOICE_PAYMENT_RECORDED` with `kind`, and the existing `CASH_COLLECTED` event (dimension = currency).

The existing `recordInvoicePayment` keeps its signature, permissions and step-up, and becomes a caller of this function with `kind = ADMIN_RECORDED`. Its behaviour is unchanged except that it now refuses a currency mismatch. Characterization tests pin today's behaviour first.

Paying never changes the billing account status automatically. A platform admin moves `GRACE` or `SUSPENDED` back to `ACTIVE` as today. Automating this is deferred.

### Online flow (SSLCOMMERZ adapter behind `PaymentPort`)

`PaymentPort` becomes: `configured`, `provider`, `createCheckout({ merchantTranId, amountMinorUnits, currency, invoiceRef, customer, urls })` returning `{ redirectUrl, sessionKey }`, `validatePayment({ valId })` and `queryByMerchantTranId(merchantTranId)`, both returning a normalized `{ status: 'VALID' | 'VALIDATED' | 'FAILED' | 'CANCELLED' | 'UNATTEMPTED' | 'EXPIRED' | 'PENDING' | 'INVALID', merchantTranId, valId, amountMinorUnits, currency, bankTranId, riskLevel, storeId }`, plus `verifyIpnSignature(form)`. Amounts are parsed from decimal strings into minor units exactly; no floating point.

1. **Start** (agency organization owner or admin only, from the agency's new Invoices page): refuse unless the invoice is `OPEN` or `PARTIALLY_PAID`, the currency is BDT and payments are configured. If an attempt for this invoice is `REDIRECTED` and younger than 30 minutes, show "A payment for this invoice was started at [time]. Check it before paying again." with Continue or Check Status. Create the attempt (`CREATED`), call `createCheckout` with success, fail and cancel URLs pointing at `/api/payments/sslcommerz/return` and the IPN URL `/api/payments/sslcommerz/ipn`, store the session key, set `REDIRECTED` and redirect. If the provider call fails or takes longer than 15 seconds, mark the attempt `FAILED` (`start_failed`) and show "We could not open the payment page. Nothing was charged. Try again." No money can have moved, because the person never reached the gateway.
2. **IPN (server to server, the authoritative trigger):** read the form body. `verifyIpnSignature` is a first filter only. A failure is audited and answered 200 with nothing applied. Then **always** call `validatePayment(val_id)` server to server. Apply only when every check passes: provider status `VALID` or `VALIDATED`; `merchantTranId` matches an attempt; store id matches configuration; amount equals the attempt amount exactly; currency equals the attempt currency.
   - `riskLevel = 1` → `HELD_FOR_REVIEW` (platform admin decides; money is not counted until approved).
   - If the attempt is already `RECORDED` → no-op (duplicate IPN, replay).
   - If `applyInvoiceCollection` returns `exceeds_outstanding` (for example a manual payment was approved meanwhile) → `HELD_FOR_REVIEW` with reason `already_paid`. Cash received is never lost: the admin sees it and refunds through the provider panel. The refund is recorded later as a `REFUND` ledger row when refunds are built.
   - Mismatched amount, currency, store or unknown `merchantTranId` → attempt (if any) `HELD_FOR_REVIEW`, audit `PAYMENT_VALIDATION_MISMATCH`, nothing recorded.
   - Provider `FAILED`, `CANCELLED`, `EXPIRED` → the attempt takes that status.
   - The provider's validation API unreachable → respond 503 so the IPN is retried, and leave the attempt for the reconciliation job.
3. **Return (browser):** never records anything by itself. It looks up the attempt by `merchantTranId`, runs the same server-side validation by `val_id` if present (idempotent; same function as the IPN), then shows one of: Payment Received, We Are Confirming Your Payment (refresh shortly), Payment Not Completed (nothing was charged), or Payment Needs a Check (we will contact you).
4. **Reconciliation job** (new `SystemScope<'process-payment-reconciliation'>`, daily cron plus a run when an admin or the agency opens the invoice): for attempts `REDIRECTED` older than 15 minutes and younger than 7 days, call `queryByMerchantTranId` and apply the same checks. After 24 hours with no success: `EXPIRED`. Late success after `EXPIRED` is still validated and recorded.
5. **Closing the payment screen:** the attempt stays `REDIRECTED` until IPN, return or reconciliation settles it.

### Manual fallback ("I Paid Another Way")

- An agency owner or admin submits a claim for an open invoice: method, reference, amount, currency, date paid, optional note. This records **nothing**. The invoice shows "Payment Reported, Waiting for Confirmation".
- A platform admin with billing permission approves (step-up, as `recordInvoicePayment` today) or rejects with a reason. Approval calls `applyInvoiceCollection(kind = MANUAL_CLAIM, sourceId = claim id)`. A refusal because of `exceeds_outstanding` is shown to the admin, who rejects the claim or records a different amount.
- Double recording (manual and online for the same money) is prevented by the outstanding-balance check under the invoice lock. Whichever comes second is held or refused, never silently added.

### Security invariants (tests required)

Spoofed browser success records nothing. An IPN with a bad signature records nothing. A valid-looking IPN whose validation says otherwise records nothing. Wrong amount, wrong currency, wrong store, unknown transaction: nothing recorded, attempt held. Duplicate IPN, replayed IPN, IPN plus return plus reconciliation for one payment: exactly one ledger row. Payment for an already-paid invoice: held, not added. A payment for invoice A cannot be applied to invoice B (`merchantTranId` binds the attempt to one invoice). Provider timeout at start: no attempt left `REDIRECTED`. Failed or cancelled: attempt status only. Late success after expiry: recorded once. Manual plus online for the same balance: second one held or refused. A non-member or a non-admin member of the agency cannot start a payment or submit a claim. Store credentials never appear in logs, audit metadata, errors or the browser.

### Configuration (owner gate)

`PAYMENT_PROVIDER=sslcommerz`, `SSLCOMMERZ_STORE_ID`, `SSLCOMMERZ_STORE_PASSWORD` (secret), `SSLCOMMERZ_MODE=sandbox|live`. The IPN URL is also set in the SSLCOMMERZ merchant panel. Readiness reports payments `available` only when all are present. Sandbox first; live only with the owner's word.

## Consequences

- **Positive:** cash in the ledger is exactly the money a provider or an admin confirmed, once. The existing billing model and admin tools keep working. A second provider (bKash, Stripe) is another `PaymentPort` adapter, not a redesign.
- **Negative:** one migration; refunds and billing reactivation stay manual; online payment is BDT only.
- **Follow-ups:** S10 (ledger and recording function, behaviour-neutral), S11 (adapter, attempts, IPN, return, reconciliation), S12 (agency Invoices page, manual claims, admin review).

## Alternatives considered

- **Trust the success redirect.** Rejected: spoofable.
- **Keep one running total without a ledger.** Rejected: idempotency and double-recording protection need one row per receipt with unique provider and source keys.
- **Stripe first.** Superseded by the owner's 26 Oct instruction (Bangladesh gateway first). Stripe remains a later adapter.

## Phase 2 (built in this programme after S12)

### Recurring period invoices (S17)

- A new system job `process-billing-cycle` (a `SystemScope`; daily cron) creates one invoice per organization per plan period. It applies when the current subscription's plan has `price_minor_units` and `currency` set and is not free:
  - The invoice period is `[period_start, period_start + plan.period_days)`. The first period starts at the subscription's `started_at`.
  - The invoice ref is `INV-<org reference code>-<YYYYMMDD of period start>`.
  - The due date is the period start plus `billing_settings.due_days` (default 7).
  - Idempotency comes from a unique index on `(organization_id, plan_id, period_start)` (migration). A rerun creates nothing.
  - The job never creates invoices for a past period older than one period: no surprise back-billing.
- Plan changes keep today's rules (`activateSubscription`, scheduled downgrades). There is no proration in V1: the new plan's first invoice starts at its own start date.
- The agency's owners and admins get an email with a "Pay Invoice" link (to the Invoices page, not a provider URL), through the existing notification outbox.

### Reminders and overdue handling (S17)

- Reminders go to agency owners and admins 3 days before the due date, on the due date, and 3 and 7 days after. They use the notification outbox, with idempotency keys of invoice plus stage.
- Overdue changes to billing status are **off until the owner sets the policy** (owner gate O13). The settings live in `billing_settings`, a single row editable by the platform owner with step-up:
  - `grace_after_days`: `ACTIVE → GRACE` when an invoice is unpaid this many days after its due date.
  - `suspend_after_days`: `GRACE → SUSPENDED`.
- These transitions are made by the system:
  - `billing_status_history.actor_account_id` becomes nullable, with a check that a null actor carries a reason starting `system:`.
  - A new column `cause` (`MANUAL | NONPAYMENT`) is added.
- **Automatic reactivation:** when `applyInvoiceCollection` leaves an organization with no overdue invoices and its status is `GRACE` or `SUSPENDED` with cause `NONPAYMENT`, it moves the status to `ACTIVE` in the same transaction (`system: paid`). A manual suspension is never lifted automatically.
- What suspension does stays exactly as today (`isBillingSuspended` and entitlements). Suspension never deletes or hides traveller-owned records.

### Refunds and overpayments (S18)

- `PaymentPort` gains `refund({ providerTransactionId, amountMinorUnits, reason })` and `queryRefund(refundId)`, for providers that support refunds (SSLCOMMERZ has a refund API; S18 re-reads the official documentation).
- **Who can refund:** platform billing staff only, with step-up, from the invoice or a held attempt. A refund can never exceed what that transaction collected, less earlier refunds.
- **The ledger row:** a `REFUND` row (negative amount, `source_id` = the refund request, unique) is written **only when the provider confirms**. Until then the refund request is `REQUESTED`, then `CONFIRMED` or `FAILED`. Invoice status is recalculated from the ledger total.
- **Held overpayments:** `HELD_FOR_REVIEW` overpayments are resolved by an admin, either "Apply to Next Invoice" (a `CREDIT` row on that invoice whose `source_id` is the held attempt, so it can be applied once; the attempt becomes `RECORDED`) or "Refund".
- **Manual payments:** money that came in manually is refunded outside VisaStack. The admin then records a `REFUND` row with a reference (step-up).

### Second provider (S19)

- A second `PaymentPort` adapter, chosen by the owner (O14), for example Stripe through a supported-country entity for USD cards, or a direct bKash or another Bangladesh gateway.
- Online checkout is offered per invoice currency by the provider that supports it.
- **Saved-card automatic charging** is allowed only through a provider that supports saved payment methods, only when an agency owner opts in, with a saved-method record (`payment_methods`: organization, provider, provider reference, last 4, expiry, created by) and a charge attempt on the due date that follows the same attempt and validation rules. SSLCOMMERZ invoices stay pay-by-link.

### Accounting export (S18)

- Platform billing staff can download a monthly CSV of ledger rows: date, invoice ref, organization reference code, kind, amount, currency, provider, transaction reference.
- No traveller data appears in it, and no formulas: every value is quoted and protected against spreadsheet formula injection.

## Implementation note, S11 (2026-10-27)

S11 is implemented: `payment_attempts` (migration 0096), the `PaymentPort` contract and `SslcommerzPaymentPort`, `packages/services/src/payments.ts`, the notification and return routes, the daily `process-payment-reconciliation` job and a signed result page. Operations: `docs/operations/online-payments.md`. Choices the ADR left open:

- **One settling function.** The notification, the browser return, the daily job and a screen refresh all call `settlePaymentAttempt`, so one payment arriving four ways is judged by the same checks and recorded once.
- **The notification names the payment; the gateway decides.** A callback body (signature included) is never evidence. It only supplies the transaction id and the validation id to ask the gateway about. A callback with no validation id (a reported failure or cancel) is confirmed by a query by transaction id, so a forged "failed" cannot close a real payment.
- **Binding.** The gateway's answer must name the attempt's own transaction id. An answer for another payment (a real validation id for payment A posted against payment B) changes nothing: it is audited and refused, and never holds B, so it cannot be used to disturb someone else's payment.
- **Ledger keys.** The ledger row's source is the attempt (kind `ONLINE`) and its provider transaction id is the gateway's validation id. The row is written with the attempt's own amount, not the gateway's, after the two were checked equal.
- **Risk.** Only a risk flag of exactly 0 is counted. 1 holds the payment (`risky_payment`); a missing or other value also holds it (`risk_unknown`), a fail-closed addition to the ADR.
- **Currency.** If the gateway reports two different currencies for one payment (a converted card payment) the payment is held as a currency mismatch.
- **Late success.** A closed attempt (failed, cancelled, expired) can still be recorded if the gateway later confirms money; only `RECORDED` and `HELD_FOR_REVIEW` are final. The daily job asks about expired payments for 7 days.
- **Rate limits.** Per network address on both public addresses, per payment on gateway calls from callbacks, and per person and agency on starting. Refused callbacks are audited at most 30 an hour in total.
- **Switches.** Everything is off unless `PAYMENT_PROVIDER=sslcommerz` and the store id, store password and `SSLCOMMERZ_MODE` (exactly `sandbox` or `live`, no default) are all set. A half-set configuration fails closed.
- **Differences from the official v4 documentation: not checked.** The documentation host could not be reached (as in the Context section). The adapter and its test double follow the widely documented v4 integration; the points to confirm against the official pages before the sandbox account is used are listed in the S11 evidence (field names `tran_id`, `val_id`, `bank_tran_id`, `risk_level`, `currency_type`, `verify_key`/`verify_sign`; the signature rule; `APIConnect`/`element` in the query reply; sandbox and live hosts; whether `val_id` is stable across queries).
